# 沉浸 × 专业：学习体验设计法

这是从一个真实项目（管理業務主任者试验学习站「William の部屋」）中，用户反复调整后形成的方法。核心只有一句：

> **每个好玩的元素都要承载学习意义；每个学习元素都要达到专业水准。** 两边缺一边，用户都会说"不对"。

## 1. 两条轴，同时检查

做任何一个功能前，先各问一遍下面两组问题，两边都答得上来才动手。

**沉浸轴（贴合学习的融入）**
- 这个元素在世界观里是什么？它和学习状态是同一件事吗？（例：窗户亮灯＝这个主题答对 8 成，不是装饰）
- 角色说话、动效、奖励，会不会打扰做题？频率和时机是否克制、体贴？
- 入口能不能用"世界里的东西"表达，而不是贴一个按钮和文字？（例：会发光的月亮＝复习笔记入口）
- 画风、配色、动作是否和已有世界统一？（新角色必须和现有角色同一画风）

**专业轴（学习要素的专业性）**
- 内容出处是否权威？（官方真题、条文、现行法；有改正就写现行规则；不确定的标"要确认"，不断定）
- 解说是否让人真正学会？（每个选项的 ○× 和理由；组合题列出每个陈述；知识点是可迁移的规则，不是抄题目）
- 结构是否符合学科本身？（复习资料按市售教材的章・节，而不是按 App 自己的分组）
- 掌握度的定义是否合理、看得见？（亮灯门槛、要复习／克服／已掌握的判定，间隔复习，再测试）
- 学习记录是否绝不丢？（本地优先保存、合并规则、备份）

详细的做法和反例见：`references/immersion.md`（沉浸）、`references/rigor.md`（专业）。

## 2. 设计流程

1. **先找学习上的目的**，再选沉浸的表现方式。问自己：用户在这一步要学会什么、要被提醒什么？
2. **把学习状态映射到世界里**：结构（科目→楼层、主题→房间）、进度（亮灯）、薄弱（发光）、克服（变绿＋✓）。一种状态只用一种视觉语言，全站一致。
3. **内容生产分工**：大量内容（提示、知识点、章节整理）交给子代理按年度／章节并行写，只允许用已有解说里的事实，写完用脚本核对"每道题都被覆盖、ID 都真实存在"，数字类的合并结果自己再看一眼。
4. **新玩法先进试验场**（如 playground 页面），质量达不到就果断删掉，不进正式版。
5. **自己验收**：手机和电脑两种宽度截图；动画暂停后按时间取帧；量出位置（如跳转后离固定标题栏 8px）。确认没问题再给用户看。
6. **需要用户拍板时**（入口放哪、克服的条件、题数），给 2～4 个选项并标出推荐，说明理由，然后按选择实现。

## 3. 和这位用户协作的方式

- 用户会发截图并用红笔圈出问题。先判断错在**理解、结构还是参数**；结构问题就从源头重做，不要一点点微调。自己做不到的（比如手绘），直接说该借助什么。
- 回复短；每次汇报最后附上两个测试链接；不重复解释。
- 用户在意时间和 token：不要"做一版→截图→再小改"地乱试，先定原因，一两次改完。
- 用户用中文或日文提问，就用同一种语言回答。

## 4. 常见失败（真实发生过）

- 装饰和学习无关 → 被要求删掉或改成入口／状态。
- 角色太吵、提弱项、显示倒计时施压 → 改成少说、体贴、只给按钮。
- 光太亮、闪烁不同步 → 改成极淡、同步或静止。
- 文字重叠、单字换行、文字压在图案上 → 一律不允许。
- 小抄只是复制题目 → 改成 2～4 行可迁移的知识点＋颜色标记陷阱。
- 复习资料按 App 结构排 → 改成教材章节。
- 克服后从错题里消失 → 错题永远保留，只标"克服"。
- 新角色和旧角色画风不同 → "像两个世界的猫"，必须统一。
